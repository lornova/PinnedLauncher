## 1. Question under test

Does a taskbar pin created from a proxy `.lnk` carrying an explicit AUMID stay a
pure launcher — never expanding in place, never merging with the launched target —
while the target opens as its **own separate button**, for each target class, on
every C-2-supported build family?

The two implementation flavors (architecture §3) split the question:

- **Flavor A (direct `.lnk`)** — does a directly-linked target associate with the
  pin's shortcut AUMID and merge into it? This is the failure mode named in
  architecture §2; A-case merges are *findings*, not protocol errors.
- **Flavor B (windowless proxy exe)** — does launching the target as a fresh shell
  activation decouple it from the pin's identity?

## 2. Decision rule

- **GO** — cases B1..B3 pass on every in-support build family (§3). Flavor-A
  results do **not** gate the GO; they feed P0.3 (flavor choice per target kind:
  e.g. A1 merging while A2 stays separate would mean flavor B is mandatory for
  plain Win32 targets but flavor A remains admissible for self-AUMID targets).
- **NO-GO** — any flavor-B case fails (merge/expand) on any in-support family:
  ADR-0006 is superseded, architecture re-opened, implementation plan rewritten
  (P0.1).
- On GO, ADR-0006 receives a dated `Amended:` annotation "verified on builds …"
  listing the families of §3 (annotation rule: ADR-0001).

Applied 2026-08-15: **GO recorded** on the §6.1 evidence, with the remaining
families reclassified from gating evidence to non-blocking confirmation runs —
rationale and tripwire semantics in §7.

## 4. Test articles

Six cases: {flavor A direct, flavor B via proxy} × {plain Win32, self-AUMID,
packaged}. All shortcuts are generated by
[`New-S3Shortcuts.ps1`](../../spikes/s3-aumid/New-S3Shortcuts.ps1) with the AUMID
stamped through `IShellLink` + `IPropertyStore` — the exact product mechanism of
architecture §2.

| Case | Flavor | Target class | `.lnk` target | Pin AUMID |
|---|---|---|---|---|
| A1 | A direct | (a) plain Win32 | `System32\charmap.exe` | `PinnedLauncher.S3.A1.PlainWin32` |
| A2 | A direct | (b) sets own AUMID | `bin\s3selfaumid.exe` | `PinnedLauncher.S3.A2.SelfAumid` |
| A3 | A direct | (c) packaged | WindowsApps alias `notepad.exe` | `PinnedLauncher.S3.A3.Packaged` |
| B1 | B proxy | (a) plain Win32 | `bin\s3proxy.exe "…\charmap.exe"` | `PinnedLauncher.S3.B1.PlainWin32` |
| B2 | B proxy | (b) sets own AUMID | `bin\s3proxy.exe "…\s3selfaumid.exe"` | `PinnedLauncher.S3.B2.SelfAumid` |
| B3 | B proxy | (c) packaged | `bin\s3proxy.exe "…\notepad.exe (alias)"` | `PinnedLauncher.S3.B3.Packaged` |

Target choices:

- **(a)** `charmap.exe` — classic unpackaged Win32 app, present in `System32` on
  every family, allows multiple instances (needed for the O5 grouping probe).
- **(b)** `s3selfaumid.exe` — built here; calls
  `SetCurrentProcessExplicitAppUserModelID(L"PinnedLauncher.S3.SelfMarker")` before
  creating its window: a controlled, canonical "exe that sets its own AUMID" with a
  known identity string. (Edge would be a real-world sample but is not installed on
  this machine; optional on matrix VMs where present.)
- **(c)** packaged Notepad via its `%LOCALAPPDATA%\Microsoft\WindowsApps\notepad.exe`
  execution alias — packaged identity
  `Microsoft.WindowsNotepad_8wekyb3d8bbwe!App`, externally verifiable through the
  oracle. Packaged on all in-scope families.

The spike AUMIDs live in the reserved namespace `PinnedLauncher.S3.*` (test-AUMID
hygiene, S-9).

## 5. Verification protocol

Numbered steps + expected observations, per the ADR-0008 interactive style. Run
once per build family, from `spikes\s3-aumid\` in PowerShell 7.

### 5.0 Preconditions and gates

1. Interactive desktop session; taskbar pinning not blocked by policy; no S3-*
   leftovers from a previous run (run `.\Remove-S3Artifacts.ps1` if unsure).
2. Record the environment (fill the header of the §6 table):
   `Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' | Select DisplayVersion, CurrentBuildNumber, UBR, EditionID`
   Also record the taskbar combine mode (Settings → Personalization → Taskbar →
   Taskbar behaviors → "Combine taskbar buttons and hide labels"; registry:
   `HKCU\...\Explorer\Advanced` `TaskbarGlomLevel` 0=always, 1=when full,
   2=never). **The O5 grouping probe is decisive only under "Always" combine** —
   with combining off, same-identity windows also get separate (adjacent)
   buttons. Set "Always" for the run and restore afterwards. O3 (pin
   association) is mode-independent and decisive in any mode.
3. Build the scratch binaries: `.\Build-S3Binaries.ps1` (needs a VS C++ toolchain).
4. Generate the shortcuts: `.\New-S3Shortcuts.ps1`
   - **Gate G0** (must print PASS for all six): every saved `.lnk` carries its
     stamped AUMID, read back by an *independent* reader (`Shell.Application`
     `ExtendedProperty`), not by the code that wrote it. If G0 fails, the
     artifacts are broken — stop, do not pin.
5. Note whether Notepad (or any target) is *already pinned* by the user on this
   machine: if so, the target lighting up **its own existing pin** instead of
   opening a new running-zone button is still a PASS for O3 (separate identity).

### 5.1 Pinning (once, all six)

6. Open Start → All apps → folder **PinnedLauncher S3 Spike** (allow a few seconds
   for Start to index new entries). For each of the six entries: right-click →
   **Pin to taskbar** (possibly under "More"). Fallback route if Start misbehaves:
   in Explorer, right-click the `.lnk` in `spikes\s3-aumid\out\` → Pin to taskbar
   (older context menu is under "Show more options"). Record which route was used.
7. **O1** — each pin appears in the pinned zone wearing the target's icon; hovering
   shows the case name (`S3-A1 plain direct`, …).
8. **Gate G1**: `.\New-S3Shortcuts.ps1 -VerifyPins` — the pin copies the shell
   placed in `User Pinned\TaskBar` still carry the expected AUMIDs. Record output.

### 5.2 Per-case click test (repeat for A1, A2, A3, B1, B2, B3 — one at a time)

Before each case: the target app is not running (close Character Map / Notepad /
s3selfaumid between cases).

9. Hover the case's pin to confirm which one it is (A1/B1 share an icon, as do
   A2/B2 and A3/B3 — the tooltip disambiguates). Left-click it once.
10. **O2** — the target's window opens. (For B cases: no visible window, console,
    or taskbar flicker from the proxy itself.)
11. **O3 (the core observation)** — the target appears as a **separate** taskbar
    button (in the running area, or lighting its own pre-existing pin — see step 5);
    the spike pin shows **no running indicator** and does not transform. FAIL =
    the pin itself gets the running indicator / the target's window sits on the
    pin's button ("expands in place").
12. **O4** — oracle: `.\Get-TaskbarIdentity.ps1 -ProcessName charmap` (or
    `s3selfaumid` / `Notepad`). Record `WindowAumid` and `PackageAumid` for the
    target's window; neither may equal the pin's AUMID. Expected values:
    - charmap: both empty (system-computed identity — see §5.4),
    - s3selfaumid: both empty is normal (process-level explicit AUMIDs are not
      externally readable; the window text shows the AUMID it set),
    - Notepad: `PackageAumid = Microsoft.WindowsNotepad_8wekyb3d8bbwe!App`.
13. **O5 — grouping probe** (behavioral identity oracle; requires "Always"
    combine, §5.0 step 2): with the pin-launched instance still running, launch
    the *same target by its normal route* (charmap: Win+R `charmap`;
    s3selfaumid: double-click `bin\s3selfaumid.exe`; Notepad: Start → Notepad).
    Expected: both instances/windows group under **one** button that is **not**
    the spike pin — proving the pin-launched instance carries the target's own
    identity, not the pin's. FAIL = the two instances land on different buttons
    with one of them on the pin.
14. **O6** — close all target windows. The pin is unchanged and a second click
    launches again.
15. Record the row in §6 (PASS/FAIL per observation, plus notes), then close
    everything and move to the next case.

Note — **unpin each A-case pin before running its B counterpart** (A1 before B1,
etc.): a direct-flavor pin targeting an exe captures that exe's windows by
target-path association regardless of who launched them (A1 finding, §6.1), so a
lingering A pin would absorb the B-launched window and muddy the observation. The
B verdict criterion is unchanged either way: the **B pin itself** stays clean.

### 5.3 Cleanup (after the family run)

16. Unpin all six (right-click each pin → Unpin from taskbar).
17. `.\Remove-S3Artifacts.ps1` (refuses to run while S3-* pins remain).

### 5.4 Oracle limits

`Get-TaskbarIdentity.ps1` reads only *explicit window-level* AUMIDs
(`SHGetPropertyStoreForWindow`) and *packaged* identities
(`GetApplicationUserModelId`). A plain Win32 target's system-computed identity, and
a process-level explicit AUMID set via `SetCurrentProcessExplicitAppUserModelID`,
are not externally readable — for those cases empty columns are expected and the
**behavioral** oracles (O3 separate button, O5 grouping probe) are authoritative.
This limit is inherent, not a script defect; it is why O5 exists.

## 7. Outcome — GO (recorded 2026-08-15)

- **Decision: GO — definitive.** The §2 GO condition (B1..B3 pass) is satisfied
  on family 26200 (§6.1). The remaining families are reclassified from gating
  evidence to risk-reduction; the project proceeds without waiting on them.
- **Rationale for closing the go/no-go on 26200 evidence alone:**
  - The question the go/no-go existed to answer — does the mechanism work at
    all on a current mainstream build? — is answered affirmatively. No single
    remaining-family result can invalidate the design; each would only narrow
    claims or trigger investigation (tripwire semantics below).
  - Decision context, recorded by the owner: the project is primarily for the
    developer's own machines, which run the verified family; working on other
    people's machines is a desirable side effect, not the goal.
  - Per-family coverage duty lives with the P2 test plan's qualification
    matrix (authoritative per C-2); the scheduled runs become its first
    entries.
- **Confirmation runs (non-blocking), tripwire semantics:** a 26100 failure
  would contradict the shared-servicing-branch expectation and demands
  investigation of the 26200 model before further reliance on it; a 28000
  failure redirects effort (investigate shell changes / alternate activation
  paths) and tempers expectations for late-2026 build families. Neither
  reverses this GO by itself.
- **Descope:** 22631 (§6.3).
- **ADR-0006:** annotated 2026-08-15 (dated `Amended:` header line, per
  ADR-0001).
- **Feed to P0.3** (flavor A vs B per target kind; finalized together with S-6
  evidence): flavor B **mandatory** for plain Win32 targets (A1
  target-path-association finding); flavor A viable but benefit-free for
  self-identifying (A2) and packaged (A3) targets — uniform flavor B is the
  KISS-consistent candidate.
