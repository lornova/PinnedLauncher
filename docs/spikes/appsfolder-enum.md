## 1. Questions and method

The add/edit dialog's installed-apps picker (management-window §5.2) plans
to enumerate `shell:AppsFolder` because it covers Win32 and packaged apps
uniformly. To close the design: (a) is enumeration fast enough on open,
(b) does it come back ordered, (c) what do the parse names (AUMIDs) look
like — the picker needs them for the S-4 deep link and target-kind
classification.

Measured via the Shell COM automation objects from PowerShell — slower
than the product's native `IShellFolder`/`IEnumIDList`, so every number is
an **upper bound**. Two warm passes, ordering vs a locale-aware name sort,
duplicate-name scan, parse-name shape histogram, and a sampled
`ExtendedProperty('System.AppUserModel.ID')` cross-check.

## 2. Results (26200.9168, it-IT, 2026-08-15)

- **166 items; full enumeration + Name + Path in ≤ 0.5 s warm** even
  through the slow automation layer (pass 1: 495 ms, pass 2: 406 ms —
  enumeration dominates; Name ≈ 23 ms and Path ≈ 1–3 ms for the whole
  list; `ExtendedProperty` ≈ 0.27 ms/item). Scaling is linear, so even a
  machine with several times the apps stays comfortably interactive, and
  the native interfaces the product will use are faster still.
- **The returned order is NOT name-sorted** (first item: *Blend for
  Visual Studio*; the sequence loosely clusters by Start-menu folder
  origin). The picker must sort itself — locale-aware by display name,
  consistent with the main list (§5.1).
- **Duplicate display names: 0** on this machine — but the picker still
  disambiguates identical names when they occur (tooltip/secondary line
  with the AUMID or publisher), since nothing guarantees uniqueness.
- **Parse-name (AUMID) shapes** — `Item.Path` equals
  `System.AppUserModel.ID` on every sampled item (0/25 mismatches):
  | Shape | Count | Example |
  |---|---|---|
  | Packaged (`Family!App`) | 42 | `windows.immersivecontrolpanel_…!…immersivecontrolpanel` |
  | Explicit dotted AUMID | 84 | `Blend.4bf05e04` |
  | `Microsoft.AutoGenerated.{GUID}` (shell-derived) | 21 | auto-ID for `.lnk` apps without an explicit AUMID |
  | **Raw filesystem path** | 18 | `C:\Strawberry\perl\bin\cpan.bat` |
  | Other bare string | 1 | `Chrome` |
  The picker cannot assume every entry has an AUMID-shaped identity: for
  path-shaped entries the parse name *is* the path. Packaged targets are
  recognizable by the `!` (feeds the P0.3 flavor decision and the
  activation route); all shapes remain valid `ParseName` inputs for the
  S-4 deep link.
- Hygiene: **no `PinnedLauncher.*` entries linger** post-S-8 (clean).

## 3. Outcome

`shell:AppsFolder` is confirmed as the picker's single source: uniform
coverage, sub-second worst-case enumeration (upper bound), identity and
display name retrievable in the same pass. Design consequences folded
into the management-window §8 question-1 resolution: the picker sorts by name itself,
disambiguates rare duplicate names, treats the parse name as an opaque
`ParseName`-able identity (AUMID-shaped or raw path), and classifies
packaged entries by the `!` separator. Enumerate on dialog open
(optionally async with a spinner as pure robustness); no caching layer is
warranted at these numbers. The optional cold-cache datum (first
enumeration after logon) can be captured post-reboot with `-Label cold`;
the warm number is the design-relevant one since the picker opens
repeatedly within a session.
